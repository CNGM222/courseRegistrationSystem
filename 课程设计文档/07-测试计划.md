## 1. 测试目标

验证三类用户能够完成已实现的业务流程，重点确认权限、选课人数、课表版本、关闭注册、成绩和账单的数据一致性。通过正常、异常、边界、并发和故障场景，发现会导致越权、超卖、部分提交、重复计费或错误展示的问题。

测试结果分为“通过、失败、阻塞、未执行、不适用”。已有测试源码、历史报告及演示运行结果只作为准备资料；本轮结论必须有对应版本、环境、时间和执行证据。

## 3. 当前业务规则与测试判定

1. 选课及授课调整要求学期为 `OPEN`，且服务端时间满足 `registrationStart <= now < addDropEnd`。恰好到截止时刻即拒绝写入。
2. 首次正式提交必须为 4 门主选、2 门备选。草稿及已有正式提交历史后的调整允许 0..4 门主选、0..2 门备选。
3. 草稿和预检不占位，也不提前释放旧注册；正式提交只注册主选，备选在关闭时才可能启用。当前提交校验针对主选的先修、容量和时间；备选的可补位性在关闭时重新判断。
4. 主选与备选之间不能重复教学班，也不能选择同一课程的不同教学班。保留本人已注册的满员班不应被当作新抢占而拒绝。
5. 先修通过要求历史学期已结束且注册已 `CLOSED`，成绩为 `A/B/C/D`；`F/I/null` 均不通过。不同快照中的同一课程按旧目录课程标识关联。
6. 时间冲突按同一实际周、同一星期及半开节次区间判断；`[1,3)` 与 `[3,5)` 不冲突。
7. 教学班容量上限 10 人，最终保留班至少 3 人。开放期不足 3 人可先注册，最终关闭再判断。当前主选注册允许无教师班，关闭时将其取消。
8. 课表、授课方案、师生资料、截止修改使用相应对象版本；更新、删除通常需要 `If-Match: "版本号"`。首次创建课表不带版本；密码重置使用 `accountVersion`，资料修改使用 `version`。
9. 教师可读本人当前及历史正式名单。写成绩要求本人授课、学期与教学班均 `CLOSED`，且北京时间当天严格晚于学期结束日期；结束日期当天仍不可写。
10. 成绩只允许 `A/B/C/D/F/I`。未录入为 `grade=null, version=null`；已有成绩版本 0 有效。省略行不变，发送空值不表示清除成绩。
11. SSN 可空；非空接受九位数字或 `XXX-XX-XXXX`，列表和详情仅回掩码。编辑留空保持原值。初始及重置密码至少 12 个字符、最多 72 个 UTF-8 字节。
12. 立即截止只阻止后续选课与授课变更，学期仍为 `OPEN`，不补位、不冻结、不计费；最终关闭需要另行执行。已截止但未最终关闭时延后截止时间，会重新满足开放写入条件，需纳入验收。
13. 关闭顺序为：检查有效人数一致性，取消无教师班，按首次提交时间及学生 ID 排序补位，再取消不足 3 人班，冻结结果并创建账单及 Outbox。补位按已提交方案的备选优先级，忽略未提交草稿；最终小班取消后不再开启新一轮补位。
14. 有正式提交历史者即使最终零门或已经撤销课表，仍产生零金额账单；仅有草稿者过期且不计费。重复关闭复用原结果，不重复补位和计费。
15. 教务最终名单仅在成功关闭后可读，只含最终 `ENROLLED` 学生的 ID、姓名、注册来源等约定标识，不含成绩和敏感资料。`pendingBillingEvents` 是关闭时摘要，当前送达情况以事件列表为准。

人数预置需同时准备实际 `ENROLLED` 记录及一致的 `enrolledCount`。只有关闭人数一致性负面用例允许刻意制造差异。各并发、关闭、删除和锁定场景使用独立数据；不可将不可逆的关闭结果作为下一用例的开放学期。

时间边界优先用后端受控 `Clock` 和前端受控时间。demo 默认只有当前学期且结束日期在未来，验证历史成绩需另建专用夹具或测试数据。H2 demo 重启会清空数据，因此持久重试和服务重启恢复应使用 MySQL。

## 5. 测试策略与优先级

按“静态核对与准备、后端自动化、前端自动化、真实 HTTP 联调、MySQL 并发与故障、专项验收、回归”执行。前端夹具测试证明界面与请求符合预期；后端 Service 测试证明业务规则；HTTP 联调证明接口链路和实际授权。三类证据分别记录。

| 优先级 | 定义 | 执行要求 |
| --- | --- | --- |
| P0 | 核心流程、越权、容量、事务、成绩与财务一致性 | 首轮必测；每次相关变更及交付前回归 |
| P1 | 常用查询、维护、错误恢复、重要边界和版本处理 | 首轮及相关模块变更后执行 |
| P2 | 展示细节、兼容性与低频异常 | 交付前及对应变更后执行 |

下列为测试场景清单。每行可按数据组合拆分子用例，使用 `原编号-01` 等后缀。每个实际执行用例都需补齐前置条件、请求或页面步骤、预期、实际结果和证据；同一场景的前端与后端执行记录必须标注层级。

## 7. 关键联合场景与数据库核对

### 7.1 三角色完整链路

1. 准备有效目录、合格教师、至少三名学生和不冲突的教学班；教师保存授课集合。
2. 学生分别保存 4+2、预检、提交；核对只有主选进入当前名单与人数。
3. 另存与提交方案不同的草稿，确认不影响有效注册；安排部分无教师主选及可补位备选。
4. 教务修改截止或立即截止；验证学生和教师变更被拒绝，但尚未产生最终名单或账单。
5. 教务执行关闭，核对取消、已提交备选补位、最终人数、学生最终课表、教务名单及账单。
6. 启动合成财务端并启用投递；观察失败、恢复、去重及 DELIVERED，确认关闭结果不随通知状态重新计算。
7. 在受控时间和专用数据下将学期置于已结束条件；教师录入成绩，学生查看本人历史与成绩单。
8. 全过程分别使用学生、教师、教务 Cookie，记录真实 HTTP 请求及数据库核对证据。

### 7.2 并发与故障方法

| 场景 | 执行方法 | 核对点 |
| --- | --- | --- |
| 抢最后名额 | 在 MySQL 用独立事务和独立学生会话；通过屏障同步提交合法方案，不以顺序请求替代并发 | 一成功一失败；目标班 10 人；失败方所有加退课不变 |
| 关闭遇在途事务 | 独立连接持有学期共享门闩，另连接关闭；释放后再关闭 | 锁持有时快速拒绝；释放后成功；H2 跳过的 NOWAIT 不计入 MySQL 通过 |
| 同版本并发编辑 | 两会话读取同一版本再同时修改课表、授课、资料或截止 | 至多一份旧版本更新成功，其他明确冲突，无覆盖丢失 |
| 关闭中途失败 | 专用测试中注入数据库异常或不变量错误，在写入账单前后检查事务 | 已提交状态与操作前一致；没有孤立关闭记录、半份账单或部分 Outbox |
| 财务确认丢失与崩溃 | 接收端接收后断开响应；重启投递服务；控制租约到期及新领取 | payload/eventId 稳定、旧租约回写无效、接收端去重、最终可恢复 |

### 7.3 必须核对的不变量

1. 每个教学班 `enrolledCount` 等于实际 `ENROLLED` 数量，且始终为 0..10。
2. 每个学生同学期有效注册不超过四门、同课程不重复；同课表同教学班不产生重复注册行。
3. 提交失败不改变原有效注册或人数；草稿与预检不改变有效注册。
4. 最终有效班有教师、状态 CLOSED、人数 3..10；取消班没有有效注册。
5. 关闭成功时课表、关闭记录、账单和 Outbox 一起提交；仅草稿者不产生账单。
6. 每学生学期仅一份逻辑账单，明细只包含最终有效班，金额和冻结 payload 一致。
7. 成绩仅对应合法有效注册；批量失败不保留部分成绩；资料删除保留历史引用。

数据库核对只在测试环境执行，证据保留合成 ID、计数和必要字段，避免输出密码摘要、密钥或完整个人标识。

| 前端开发/执行人员 | 交互、契约请求、浏览器与视口测试、状态恢复及字段错误验证 |
| 环境与验收人员 | 数据库和依赖环境、HTTPS、专项负载与恢复、剩余风险接受及验收结论 |

同一人可承担多个角色，但执行记录需有明确责任人。外部环境未就绪不阻止其他独立场景执行。
