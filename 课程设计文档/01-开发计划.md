## 1. 项目目标与范围

### 1.1 项目目标

完成一个可运行、可演示、可测试的课程注册系统，使学生能够制定课表、选退课和查看成绩；教师能够选择授课班、查看名单和录入成绩；教务员能够维护师生信息并关闭注册。

系统应实现从课程目录查询、四门主选与两门备选、注册提交，到关闭注册、备选补位、课程取消和财务通知的完整业务链路。重点保证容量上限、数据归属权限和事务一致性。

### 1.2 交付边界

| 类别 | 本期交付 |
| --- | --- |
| 应用 | Vue 前端、Spring Boot 后端、MySQL 建库迁移与演示数据 |
| 外部集成 | 旧课程目录只读适配器、独立目录模拟数据源、财务通知接口及模拟接收端 |
| 本次文档 | 开发计划、需求分析文档、设计文档，各提供 Markdown 和 Word 版本 |
| 后续课程材料 | 测试计划、测试报告、个人工作总结、小组总结、运行与部署说明 |
| 演示资产 | 三类角色账号、当前及历史学期数据、边界场景数据、演示步骤 |

真实 Ingres 数据库和真实财务接口依赖外部环境。本期须先完成可替换适配器及模拟联调，并分别报告“模拟验收”和“真实对接”的状态，不能以模拟结果宣称真实系统已接通。

### 1.3 不纳入本期的功能

不开发在线支付、课本订购、招生、毕业审核、自动排课和移动原生客户端。不维护旧目录中的课程名称、学分、先修关系和教学安排。不处理关闭注册之后的换教师、重开注册、退费和跨系统人工调账。

## 2. 实施策略与技术路线

### 2.1 组织方式

采用短迭代开发，按“需求基线、技术验证、完整业务闭环、稳定验收”推进。每周五检查实际成果，每次迭代均包含需求澄清、开发、测试和文档同步，不将测试全部留到最后一周。

本计划从课程给定的 9 月 8 日起排期；编制日为 9 月 9 日。9 月 8 日任务作为第一周内补齐的计划事项，不记录为已经完成。所有完成情况以后续提交记录和验收证据为准。

### 2.2 技术基线

| 层次 | 选型 | 用途 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus | 三角色业务界面、表单与课表状态 |
| 后端 | Java 21、Spring Boot 3、Spring MVC、Spring Security、Bean Validation | REST 接口、登录授权、业务事务 |
| 数据访问 | MyBatis、MySQL 8.0、InnoDB、Flyway | 可控 SQL、行锁、结构迁移 |
| 会话 | Spring Session JDBC | 服务端会话及多实例共享登录状态 |
| 接口与测试 | OpenAPI、JUnit 5、Spring Boot Test、Vitest、Playwright、JMeter | 接口契约、单元与集成测试、业务验收、压测 |
| 部署 | Nginx、可选 Docker Compose、Git | 同源反向代理、环境复现和版本管理 |

项目初始化时选择 Spring Boot 3 系列中仍受维护的补丁版本，固定 Java、Node.js、依赖版本及锁文件；本计划不预先声称某个补丁是最新版本。Maven 与 npm 依赖由组内验证后统一冻结。

采用模块化单体架构。Redis、消息中间件和微服务不作为课设必需依赖。旧目录通过同步快照降低访问压力，财务通知通过 MySQL 事务消息表和定时重试实现可靠投递。

### 4.2 依赖与关键路径

需求规则确认 → 数据模型及接口契约 → 身份与目录基础 → 并发选课 → 关闭注册与财务 → 完整验收 → 运行检查。

教师页面和教务维护可以与学生选课并行开发。关闭注册开发必须依赖已经稳定的课表状态、人数统计和授课关系；财务通知依赖关闭注册生成的最终课表及费用快照。

若进度落后，先压缩图表美化、额外查询和非必需导出功能；容量控制、越权保护、关闭注册、可靠通知与八个核心用例不能降级为演示假数据。

## 6. 开发、协作与配置管理

### 6.1 日常协作

每日进行约 10 分钟进度同步，报告完成项、下一步及阻塞。每周至少一次集成演示。业务争议记录到决策表，以需求编号、采用解释、影响范围和评审结果形成可追溯记录。

需求变更须记录原因、影响的接口、数据库、测试及工时。A 组织评估后更新需求和设计版本，明确由哪次迭代实施。未确认的增量功能进入待办列表。

### 6.2 仓库与提交

建议单仓库目录为 frontend、backend、integration-mocks、database、docs、deploy。main 保持可构建，日常使用短期 feature 分支；合并前至少由另一成员检查业务影响、测试结果和敏感数据处理。

提交说明关联需求或缺陷编号，例如 feat(FR-03): 实现课表提交。发布标签对应迁移脚本、配置示例、演示数据和文档版本。数据库结构变更使用新增 Flyway 迁移，不改写已执行的共享迁移。

真实密码、数据库连接凭据、会话密钥及真实身份证明信息不进入版本库。演示账号使用独立合成数据，密码由初始化脚本从本地配置读取。

### 6.3 完成定义

一个功能只有在代码评审完成、相关自动化检查通过、错误与空状态可操作、对象权限有效、接口与数据字典同步且验收记录存在后才视为完成。页面能够打开或接口返回成功不足以证明业务完成。

## 7. 验证安排

### 7.1 风险驱动验证

| 验证主题 | 方法与预期证据 | 安排 |
| --- | --- | --- |
| 最后一个名额 | MySQL 上并发提交到已有 9 人的教学班，仅一人成功，最终 10 人 | I1 原型、I2 回归 |
| 一次提交的一致性 | 多门主选中一门失败，全部新增、退课及计数回滚 | I2 |
| 草稿不占位 | 保存四主选两备选草稿，教学班人数不变；已注册课表另存草稿不释放现有名额 | I2 |
| 关闭与在途请求 | 存在选课事务时关闭返回冲突且状态不变；成功关闭后新写请求拒绝 | I3 |
| 取消与备选 | 无教师、2/3/10 人边界、两备选顺序、补位后最终复核 | I3 |
| 外部故障 | 目录超过超时阈值、财务先失败后恢复、消息重复与崩溃重发 | I3、I4 |
| 成绩与越权 | A/B/C/D/F/I 及留空；学生访问他人成绩；教师修改非本人教学班 | I3、I4 |
| 性能 | 固定硬件、数据量、思考时间和操作比例，记录 500 本地及 2000 总用户场景 | I4 |
| 备份恢复 | 将备份恢复至隔离数据库，核对课表、人数、成绩和待发消息 | I4 |

事务和并发测试使用真实 MySQL 8 环境，不以 H2 等数据库结果替代 InnoDB 锁语义验证。财务模拟端须实现幂等键去重，并能人为切换超时、拒绝和成功响应。

### 7.2 验收口径

功能验收以需求文档 AC-01 至 AC-18 为主，验证八个核心用例及关键异常。严重程度分为 P0（数据损坏、泄露或核心流程不可用）、P1（关键规则错误）、P2（局部功能问题）、P3（外观问题）。发布时 P0/P1 必须清零，P2 必须评估影响并形成记录。

2000/500 同时在线、旧目录不超过 10 秒、80% 事务在 2 分钟内完成均作为验收目标；具体硬件容量须实测。若没有满足规模的环境，报告已验证的上限与未验证项，不写“全部达标”。

## 8. 风险与应对

| 风险 | 影响 | 应对及触发条件 | 主责 |
| --- | --- | --- | --- |
| 规则歧义 | 备选、计费或关闭行为不一致 | I0 逐条评审需求文档 AD-01 至 AD-12；修改时同步测试 | A |
| 抢课超卖或死锁 | 人数超过 10、数据不一致 | I1 验证行锁、锁顺序、原子更新；发现超卖即阻断合并 | C |
| 关闭过程中部分落库 | 课表、取消与计费不一致 | 单个本地事务、影子计算、故障注入与回滚校验 | A、C |
