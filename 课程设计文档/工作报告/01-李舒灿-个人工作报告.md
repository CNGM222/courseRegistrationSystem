## 二、职责与工作目标

我与李舒灿共同承担系统的主要技术工作，我侧重需求到后端实现的转化。我的目标是建立清晰的角色权限和数据模型，使学生选课、教师授课、教务关闭注册及计费组成相互一致的业务流程。设计时，我既考虑正常操作，也关注重复提交、容量竞争、截止变化和外部依赖失败，避免界面显示成功而数据只完成部分修改。

## 三、分阶段具体工作

### 1. 需求与业务边界整理

我围绕学生、教师和教务员三类角色梳理操作入口、权限范围及状态变化，明确学生只能处理本人课表和成绩，教师只能访问本人授课班的正式名单，教务员负责师生维护、截止控制和最终关闭。对于选课，我区分草稿、预检和正式提交：草稿最多保存四门主选、两门备选，首次提交必须满足四主选两备选，后续调整最多保留相同上限；备选不立即占用名额，关闭时依据已提交方案参与补位。

同时，我将“立即截止选课”与“最终关闭注册”作为不同业务动作。截止只终止后续选课或授课变更，最终关闭才处理取消、补位、最终名单与账单。教师当前名单只读，成绩录入须同时满足学期已结束、学期和教学班均已关闭，防止权限与时间条件混淆。

### 2. 架构与数据库设计

我采用 Spring Boot 4.1.1、Java 21、Spring Data JPA、Spring Session JDBC 和 MySQL 9.6，按 Controller、Service、Repository 组织后端。接口返回专门的 DTO，避免直接暴露实体及敏感字段。数据库围绕账号、师生、学期、目录快照、教学班、课表修订、注册记录、成绩、账单和 Outbox 等对象建立关联，并利用唯一约束和版本字段表达业务限制。

课表同时保留草稿指针与已提交指针，使新保存的草稿不会覆盖已经生效的注册。课程信息关联目录快照，历史课表保留可显示的冻结信息，减少外部目录变化对既有业务的影响。金额采用精确十进制类型，账单明细依据最终有效注册形成，避免前端显示数值反向决定计费结果。

### 3. 认证与选课核心实现

我重点承担会话认证和选课事务部分。认证使用 Cookie 会话、CSRF 校验及 BCrypt 密码摘要，结合停用、失败锁定和会话撤销限制非法访问。角色及本人身份由服务端确定，不能依赖前端隐藏按钮实现授权。

选课提交在事务中重新验证开放状态、草稿修订、课表版本、先修课、时间冲突和容量。通过学期门闩、课表及教学班锁协调并发操作，并在锁定资源后核对版本。预检只提供当时的检查结果，不承诺保留名额；正式提交失败时，原有效注册和人数修改一并回滚。教师授课、成绩和人员维护也遵循权限、状态及关联约束，保持统一的业务处理方式。

### 4. 关闭注册与账单设计

我将关闭过程组织为一个完整事务：先核对教学班人数与有效注册数，取消无教师班，再按首次提交时间、学生标识和备选优先级处理可补位方案，最后取消不足最低人数的班并生成最终结果。有效班人数范围为 3 至 10，学生有效课程不超过四门，补位仍须满足容量、先修及时间限制。

关闭记录、最终课表、账单和 Outbox 事件共同提交。仅保存草稿的学生不生成账单，已提交学生按最终有效课程计费。财务通知交由独立投递机制处理，不把远程网络请求放入关闭主事务；重复关闭查询已有结果，避免重复计算费用。

## 六、困难与解决思路

本阶段最需要谨慎处理的是状态与并发相互影响。我通过分离草稿和提交状态、锁后校验版本及事务回滚降低覆盖和部分提交风险。关闭流程涉及多类数据，我把人数、有效班和账单规则作为不变量进行检查，使错误能够中断整个关闭操作。安全方面，我将权限校验放在服务端，并在敏感标识处理和日志输出中限制暴露范围。
